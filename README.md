# zipfix

修一个很多人都遇到过、又说不清的问题：**从网上下的压缩包，解出来文件名全是乱码。**

不用装 PeaZip，不用改系统语言，不用重下。一条命令。

```
python zipfix.py list 你的压缩包.zip      # 先看会改成什么
python zipfix.py fix  你的压缩包.zip      # 生成修好的包
```

---

## 为什么文件名会乱码

压缩包里的文件名不是文字，是**字节**。同一个字节序列，用不同编码去解释，会得到完全不同的文字。

Windows 上很多压缩工具（尤其是日文、繁体环境的）写文件名时没标 UTF-8，用的是本地编码：中文 Windows 是 GBK，日文 Windows 是 Shift-JIS。解压软件遇到这种包，一般按 CP437（DOS 时代的国际编码）去解，就得到一堆 `╓╨╬─▓Γ╩╘` 这样的怪符号。

**关键点：文件本身没坏，内容一个字节都没丢。** 只是名字被解释错了。所以这件事是可逆的——把字节读出来，换对的编码再解释一遍就行。

这就是为什么"重新解压一遍"没用：复用的是同一个错误解释；也是为什么改用 PeaZip 手动选编码能好：它让你指定编码。

zipfix 做的事就是自动把这个编码猜对。

---

## 怎么猜的

如果压缩包标了 UTF-8 标志位（zip 格式里 general purpose bit 11），那文件名一定是 UTF-8，直接放过，不动。

没标的时候，把原始字节挨个用候选编码解一遍（UTF-8 / GB18030 / Big5 / CP932 / EUC-KR / CP437），给每个结果打分：

- 解出高频常用字（"文件""文档""报告"这些）→ 高分
- 解出日文假名、韩文音节 → 高分
- 解出控制字符、私用区字符、制表符区（`╓╨` 那种）→ 扣分
- 解出一堆生僻字 → 只给很少的分

取分最高的那个。只有分数明显高于原名（默认高 3 分）才动手，否则原样保留——**宁可不动，也不改错。**

这一步很重要：GBK 和 Shift-JIS 的字节范围是重叠的，光看"能不能解成汉字"分不出对错，很多工具就是在这里判错的（把日文包错当成中文 GBK 解）。

## 真实测试

造了两个测试包：一个是 GBK 文件名且没标 UTF-8 的真乱码包，一个是日文 Shift-JIS 包。

中文包：

```
$ python3 zipfix.py list gbk.zip
发现 3 处文件名乱码:

  ╓╨╬─▓Γ╩╘.txt
    -> 中文测试.txt   (按 gb18030 解出)
  ╦╡├≈╬─╡╡.md
    -> 说明文档.md   (按 gb18030 解出)
  docs/─┌▓┐▒╩╝╟.txt
    -> docs/内部笔记.txt   (按 gb18030 解出)
```

日文包（这里最容易判错，很多工具会当成中文）：

```
$ python3 zipfix.py list jp.zip
发现 1 处文件名乱码:

  ô·û{îΩâeâXâg.txt
    -> 日本語テスト.txt   (按 cp932 解出)
```

修复后，压缩包内所有文件的内容 md5 与原包完全一致——**只改名字，不动内容。**

正常 UTF-8 包：`没有发现文件名乱码。`，不会被误改。

## 用法

| 命令 | 作用 |
|---|---|
| `python zipfix.py list <包>` | 列出每处乱码会改成什么，不改文件 |
| `python zipfix.py check <包>` | 只检查，有乱码时退出码 = 1（可放进脚本） |
| `python zipfix.py fix <包> -o 新包.zip` | 生成修好的包 |
| `python zipfix.py fix <包> --inplace` | 直接覆盖原文件 |

`fix` 默认输出到 `<原名>-fixed.zip`，不会动原文件。

零依赖，Python 3.6+ 就能跑，不用 pip 装任何东西。

## 已知局限

- **只支持 zip**。RAR、7z 的文件名编码结构不一样，暂不支持；这两种用 7-Zip 命令行也可以：`7z x 包.rar -mcp=932`（932 是日文，936 是简体中文）。
- **加密/分卷 zip** 解不开，脚本会提示这不是有效的 zip。
- 打分是启发式的，不是 100% 准。所以 `list` 是独立命令——**先看再改**，觉得不对就别 `fix`。
- 文件名之外的元数据（注释、扩展字段）重新打包时会丢，只保留文件名、时间戳、压缩方式。

## 什么时候用不上

如果你的乱码是**打开文件后内容乱**（比如 CSV 里中文变成 `锟斤拷`、Excel 打开一堆方块），那不是文件名问题，是内容编码问题。文件名修好也解决不了，别用这个。

那种情况我另有一个判断口径：CSV 的经典症状是"WPS 能开、Office 乱码"——说明字节是 GBK、但文件声明自己 UTF-8；反过来"Excel 能开、记事本打开是乱码字节"就是缺 BOM。
